## Long Messages And Links

Messages wrap long text and links; `pre` blocks scroll within their message body instead
of widening the transcript. Keep readable link text and native keyboard focus.
Scrollable code blocks should use `tabindex="0"` and a descriptive accessible
label so Safari keyboard users can reach and scroll them.
Transcript height, message updates, announcement policy and scroll-indicator
navigation belong to the application. Existing `chat-scroll` / `data-chat-tl`
contracts remain unchanged. Do not treat timeline styling as automatic message
loading or scroll-position management.

# Chat

Chat provides CSS-only primitives for agent conversations. User messages appear in rounded bubbles; agent answers render directly in the transcript, with optional avatars, activity disclosures, reasoning traces, tool calls, and streaming states.

## Basic Usage

Use `.chat.chat-end` with `.chat-bubble` for user messages. Use `.chat.chat-start.chat-agent` with `.chat-content` for agent output: it takes the available width with no bubble background, border, or padding. Put any existing `.avatar` inside an optional `.chat-avatar`; omit the slot when no avatar is needed. Start and end alignment follow the text direction, including RTL transcripts.

Wrap a transcript in `.chat-scroll` when the conversation should scroll inside a fixed-height panel. Scroll behavior defaults to `smooth`. Pair **agent replies** with matching indicators via `data-chat-tl` so Scroll-Driven Animations can sync the rail with visible assistant rows.

## Agent Answers And Activity

Keep the answer in a direct `.chat-content` block, adding `.markdown-body` for rich text.
Group work records in native `<details class="chat-work">` with a `.chat-work-summary`
and `.chat-work-body`. The compact summary can show **Worked**, tool or command counts,
and failed operations; the application supplies those labels and values.

Place the work disclosure before a completed answer. During progress, a brief content
update may come first, with the activity summary below it. The answer stays visible
when the work disclosure is closed. Reasoning and tool records can be nested inside
the work body or placed directly in the agent row. All disclosures use native
`<details>` / `<summary>` interaction and need no toggle script.

This static example illustrates completed checks and a pending preview retry; it does
not execute tools or make network requests.

## Collapsible Sent Messages

Add `.chat-bubble-collapsible` to sent **user** bubbles to keep messages taller than
six rendered lines compact. Put the message text in a direct `.chat-bubble-content`
child and a native `.chat-bubble-toggle` button after it. The collapsed content preserves
newlines and wraps naturally; **Show more** reveals the complete message and changes to
**Show less**. Short messages and messages of exactly six rendered lines need no toggle.
Assistant replies and waiting queue items keep their existing presentation.

```html
<div class="chat chat-end">
  <div class="chat-header">You</div>
  <div class="chat-bubble chat-bubble-primary chat-bubble-collapsible">
    <div class="chat-bubble-content" id="demo-long-message" tabindex="-1">Review the chat view.

Keep multiline text.
Check keyboard focus.
Check narrow screens.
Share the results.</div>
    <button class="btn btn-ghost btn-xs chat-bubble-toggle" type="button"
      aria-controls="demo-long-message" aria-expanded="false" hidden>Show more</button>
  </div>
</div>
```

The application wires the toggle and decides when it is needed. After rendering, compare
the content's natural `scrollHeight` against `6 * parseFloat(getComputedStyle(content).lineHeight)`,
allowing one pixel for rounding. Reveal the button only when content exceeds that limit.
On click, switch its `aria-expanded` value and **Show more** / **Show less** label;
core CSS reads `aria-expanded="true"` to remove the height limit. Give each content
element a unique ID and reference it through `aria-controls`.

Use `ResizeObserver` to remeasure actual wrapped lines when the available width changes,
and refresh after message text updates (or observe them with `MutationObserver`). If a
message becomes short enough, hide its button and reset `aria-expanded` to `false`.
Before hiding a focused button, move focus to the controlled content with `tabindex="-1"`.
Disconnect observers when removing messages or leaving the page. The demos use a shared
controller with cleanup on Astro navigation; this controller is documentation code,
and core remains CSS-only. Sent, steered, and automatically dispatched user messages
in the waiting-queue demo all use this same behavior.

## Waiting Queue And Steer

Keep messages sent during an active reply in a separate `.chat-queue`, in sending order.
A waiting message enters the transcript when the application dispatches it after the
current reply completes. **Steer** dispatches that message immediately: remove it from
the waiting queue, add its user row to the current conversation, and use it to guide
the active reply. Steer does not cancel the active reply or start another assistant turn.
**Remove** discards a waiting message without sending it.

This demo starts with an active simulated reply and two waiting messages so the queue
is visible immediately. Use a row's **Steer** to add it to the same current reply, or
**Complete response** to finish that reply and send the oldest waiting message first.
**Start fresh** returns to the idle greeting. The demo has no backend or generated answer.

<ChatQueueDemo />

Place the queue and composer in one `.chat-input-area`. The queue forms a shallow,
inset tray tucked behind the rounded composer, with one message per row and no
individual card borders or colored fills. A leading `.chat-queue-icon` introduces the
single-line preview; a native `title` preserves the full message. Keep the queue's
accessible heading and ordered positions visually hidden, and announce the waiting
count through the polite status region. Every row keeps its plain **Steer** action
and icon-only Remove action available. The application still marks the next message
with `.chat-queue-item-active` and updates its position when the queue changes; the
leading icon provides emphasis without an active border highlight.

Multiple rows share the same tray. Add an optional `.chat-queue-attachment` thumbnail
beside a message preview when the caller already has attached media. The caller supplies
the image source and meaningful alternative text; this presentation primitive does not
upload files or manage attachment state. The live demo uses text-only drafts.

Use `.chat-composer` with a labelled native `.chat-composer-input` textarea and adjacent
ghost actions. The primary action reads **Send** while idle and **Queue** during a reply.
The composer's **Steer** action sends the current draft directly into the active
conversation without adding it to the waiting queue. It is disabled while idle.
The draft clears only after successful admission; blank drafts are rejected. Use
`.chat-composer-ghost` for the reference's transparent border while retaining its
keyboard focus treatment.

| Key | Action |
|---|---|
| `Enter` | Send while idle; queue while a reply is active |
| `Shift+Enter` | Insert a native textarea newline |
| `Ctrl+Enter` or `⌘+Enter` | Steer the current draft immediately while a reply is active |

Ignore shortcuts during input-method composition, including `isComposing` and legacy
key code `229`, so pressing Enter to confirm an IME candidate never sends the draft.
Keep the native textarea's selection, editing, and resize behavior. **Complete response**
is a separate demo control that simulates completion; it is not a composer action.

network requests, steering support, and keyboard handlers. Wire Enter to the form's
native submission and Ctrl/⌘+Enter to immediate steering, keeping Shift+Enter native.

a stable identity so a completed or steered message cannot be dispatched twice. Hide an
empty queue with `hidden` rather than leaving an empty panel in the layout.

## Scroll-Driven Indicators

`.chat-scroll` hoists named view timelines with `timeline-scope` (`--chat-1` … `--chat-24`). Pair **agent / assistant rows only** (`.chat-start`) with matching indicators: `.chat[data-chat-tl="N"]` declares `view-timeline-name`, and `.chat-scroll-indicator[data-chat-tl="N"]` binds `animation-timeline` + `animation-range: entry 0% exit 100%`.

User turns stay in the transcript but do not get ticks. Click an indicator to jump to that agent response **inside** `.chat-scroll` — use `button` + `data-chat-target` (not bare `href="#…"`), otherwise the document will scroll. Docs demos wire the click handler; app code should call `scroller.scrollTo(...)` the same way.

The dashes keep their visual spacing, while adjacent buttons have continuous hover and click areas. Moving through the space between dashes still selects an indicator.

Requires a browser that supports Scroll-Driven Animations. Unsupported browsers still scroll smoothly; indicators stay in the idle style.

Keep `.chat-input-area` outside `.chat-scroll` so the composer stays visible while
browsing replies. Connect the Send button to your application's message handler.

## Message Status And Actions

Place `.chat-status` below agent content or a user bubble to show generation state, token speed, and token count. Group each metric in `.chat-status-item` and emphasize its number with `.chat-status-value`. Metrics wrap on narrow screens and use tabular numerals.

Use `.chat-actions` for a row of existing buttons. Add `.chat-actions-hover` to reveal the actions when the message is hovered or contains keyboard focus. Actions remain visible on devices without hover. Omit the modifier when actions should always be visible.

Use square icon buttons with descriptive `aria-label` attributes. Pair each button with a native [Tooltip](/duskmoonui/docs/en/components/tooltip/) through `interestfor` and `aria-describedby` to show its action name.

The application supplies status text and metric values and handles each action. The buttons below demonstrate styling; they do not edit, retry, copy, or stop a response.

## Accessibility

- Use visible text for tool statuses such as `Pending`, `Running...`, `Done`, and `Failed`.
- Add `aria-label="Agent is typing"` to the content that contains `.chat-typing`, or let the application announce the state through a polite status region.
- Use native `<details>` and `<summary>` for activity, reasoning, and tool records so keyboard interaction works without custom JavaScript. Keep work counts and failures readable as text; keep the final answer outside the disclosure.
- Use native buttons for message actions, with descriptive accessible names when repeated labels need context. Hover actions reveal when a button receives keyboard focus; they remain visible on touch devices without hover.
- Keep status and token metrics readable as text. Let the application choose which state changes to announce; avoid announcing every token-count update.
- Use a native Show more / Show less button for long sent messages, with `aria-expanded` and `aria-controls` synchronized to the controlled content. Hide it for six or fewer rendered lines; move focus to the content before hiding a focused toggle after remeasurement.
- Name the waiting queue and its list. Keep `role="list"` when list markers are removed, and use `tabindex="0"` with an accessible name on the scrollable list so keyboard users can scroll it.
- Give repeated Steer and icon-only Remove buttons names that identify their waiting message. Keep all row actions reachable, including rows after the next message to dispatch. After consuming or removing a focused queue row, move focus to a surviving row action or the message textarea.
- Announce queue transitions and the waiting count through one polite `role="status"` region. Avoid announcing the same change through a live transcript as well.
- Label the native textarea. Show keyboard hints and expose shortcuts through `aria-keyshortcuts`; use Shift+Enter for newlines and never dispatch during IME composition. Render user input as text, such as with `textContent`, instead of interpolating it into HTML.
- `.chat-scroll` respects `prefers-reduced-motion` by switching `scroll-behavior` to `auto` and disabling indicator animations. Give the scroll container a reachable height. Map ticks only to agent reply starts. Prefer `<button data-chat-target>` over hash links so navigation stays inside the panel; give each indicator an `aria-label`.
