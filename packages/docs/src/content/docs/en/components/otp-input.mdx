# OTP Input

Prefer one native text input containing the complete code. It exposes one accessible label
and one submitted value. Leading zeros, paste, selection, replacement, deletion and reset
remain ordinary browser editing behavior.

## Imports

Individual example prerequisites (including composition and demo actions):

```css
@import "@duskmoon-dev/core/base.css";
@import "@duskmoon-dev/core/themes/sunshine";
@import "@duskmoon-dev/core/components/otp-input.css";
@import "@duskmoon-dev/core/components/form-group.css";
@import "@duskmoon-dev/core/components/button.css";
```

`base.css` supplies global focus/utility definitions and shared spacing/shape tokens;
use your framework reset when appropriate. Substitute the Moonlight theme for dark forms.

Aggregate: `@duskmoon-dev/core` with Tailwind v4; no-Tailwind: `@duskmoon-dev/core/standalone.css`.
Individual: `@duskmoon-dev/core/components/otp-input.css` plus a theme/reset and
`form-group.css` for labels/help. Extensionless `components/otp-input`
exports generated `css` and constructable `styles`, with no interaction runtime.

## Single Native Input

The compact input fits four or six monospace characters. Each decorative underline aligns
with one character, not a separate field. The complete code and caret remain visible above
the guides. No hidden mirror input,
letter-spacing, pointer suppression or extra accessibility-tree elements are used.
Without background enhancement this is still a usable ordinary text input. In a container
too narrow for the complete code, the native input scrolls while editing rather than clipping
or hiding the caret; guides do not implement character selection or focus movement.
An adjacent `.validator-error` reserves its layout space while hidden, so revealing an
error on blur does not move the Reset button during a click.

    <p id="demo-otp-six-help" class="validator-hint">Enter the complete six-digit code.</p>
    <p id="demo-otp-six-error" class="validator-error">Error: enter exactly six digits.</p>

<ComponentShowcase title="Four-character code" code={`<form>
  <label class="form-label" for="demo-otp-four">Verification code (4 digits)</label>
  <input id="demo-otp-four" name="short-code" type="text" class="otp-code otp-code-4 otp-code-secondary validator" autocomplete="one-time-code" inputmode="numeric" minlength="4" maxlength="4" pattern="[0-9]{4}" required value="0012">
  <button class="btn" type="reset">Reset to 0012</button>
</form>`} />

Use `type="text"`, not number: number controls lose leading-zero semantics and do not
support text length/pattern constraints. `inputmode` suggests a keyboard; it does not
restrict characters. The `otp-code-4` class changes only the length guide; HTML constraints
must match. Alphanumeric codes can use an appropriate native pattern and text input mode.

Colors: `.otp-code-primary`, `secondary`, `tertiary`, `info`, `success`,
`warning`, `error`. Focus and disabled states use native state.
Native success requires `.validator.validator-success`; an ordinary success color class
does not prove that a code was accepted. Follow the
[Validator contract](/duskmoonui/docs/en/components/validator/) for explicit error precedence.

## Retained Segmented API

Segmented fields are retained for existing integrations. Core supplies **styling only**.
An application controller must implement focus movement, backspace/arrow handling,
paste distribution, one-value aggregation, error association and reset synchronization.
Do not submit several same-name single-character inputs as though they were one code.

This disabled styling sample deliberately does not advertise a runnable segmented widget:

<div style={{ overflowX: 'auto' }}>

| Canonical class | Compatibility / role |
| --- | --- |
| `.otp-input`, `.otp-input-field` | Segmented wrapper/field |
| `.otp-input-underline` | Alias `.otp-input-underlined` |
| `.otp-separator` | Alias `.otp-input-separator`; decorative, hide from AT |
| `.otp-helper` | Alias `.otp-input-helper` |
| `.otp-error-message` | Alias `.otp-input-helper-error` |
| `.otp-input-helper-success` | Optional success text presentation |
| `.otp-input-sm/lg`, `compact/wide` | Segment sizing/gaps, wrapping on narrow layouts |
| `.otp-input-outlined/filled/ghost` | Segment appearance |
| `.otp-input-{color}` | primary/secondary/tertiary/info/success/warning/error/accent/neutral/base |
| `.otp-input-field-filled`, `.otp-input-masked` | Legacy visual presentation, not behavior |

</div>

Old documentation's `otp-input-4/6`, `otp-input-disabled` and
`otp-input-field-focused` are not supported APIs. Count real fields, set actual
`disabled`, and use actual focus. Masking is browser-specific and does not secure a code.

## Verification Boundary

Automated checks cover text editing, synthetic clipboard paste, selection, native constraints,
FormData, reset and styling. `autocomplete="one-time-code"` requests platform support:
real SMS delivery, device autofill and mobile keyboard behavior require separate device tests.
No device-level autofill verification is claimed.
